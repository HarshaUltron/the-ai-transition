Chapter 02

The Software Team

To understand what AI could change, it helps to first look at how software is traditionally built.

A software project is rarely just one person sitting in front of a computer writing code.

There are usually multiple roles involved.

The Developer

The developer turns requirements into working software.

They write code, build APIs, connect databases, implement business logic, fix bugs and integrate different systems.

For a long time, this was considered one of the most technically demanding parts of software development.

The QA Engineer

Then there is QA.

The QA engineer tests what the developer built.

They think about what could go wrong, create test cases, reproduce bugs, validate fixes and make sure the software behaves as expected.

Their job isn't simply to confirm that the happy path works.

It is to find the paths nobody thought about.

The DevOps Engineer

Then comes infrastructure and deployment.

Someone has to make sure the application can actually run.

Cloud infrastructure, containers, CI/CD pipelines, networking, monitoring, secrets, scaling and production deployments all become part of the picture.

That is where DevOps and platform engineers come in.

The Architect

Above the implementation details, there is architecture.

Someone has to decide how the different components should fit together.

Should the system use a monolith or microservices?

Which database should be used?

Where should caching happen?

How should the system scale?

What happens if a service fails?

How do we keep the system secure and maintainable?

These decisions can affect a system for years.

The Manager

And then there is management.

Someone has to understand the business requirement, coordinate people, manage timelines, communicate with stakeholders, resolve dependencies and make sure the team is actually delivering what the business needs.

So a typical software project might look something like this:

Requirement → Design → Development → Testing → Deployment → Monitoring → Delivery

Different people may own different parts of that process.

Now comes the interesting part.

What if we give AI the whole problem?

Most conversations about AI and software development focus on individual tasks.

"Can AI write this function?"

"Can AI create a unit test?"

"Can AI fix this bug?"

"Can AI deploy this application?"

But what if we stop thinking about these as separate tasks?

What if I give AI everything at once?

Imagine that I give an AI system the complete business requirement, the problem we are trying to solve, the expected outcome, the existing codebase, the database schema, the technical constraints, the security requirements, the deployment environment and all the other context that the team would normally need.

And then I give it one big instruction:

"Understand this problem and build the complete solution."

Now imagine what that system could potentially do.

It could break the requirement into smaller tasks.

It could propose an architecture.

It could write the implementation.

It could create tests.

It could analyse test failures and modify the implementation.

It could generate documentation.

It could prepare deployment configurations.

It could interact with cloud infrastructure.

It could monitor the system and respond to failures.

And if multiple AI agents are working together, each one could potentially handle a different part of the workflow.

At that point, we are no longer asking:

"Can AI write code?"

We are asking something much bigger:

"If one sufficiently capable AI system can perform the work traditionally distributed across developers, QA engineers, DevOps engineers and even parts of architecture and project coordination, what happens to the team that used to perform that work?"

The uncomfortable thought

This is where the question becomes difficult.

Because if AI can perform individual tasks, we can simply say that engineers will use AI as a tool.

But what if the tool becomes capable of performing an entire workflow?

What if the developer doesn't disappear, but one developer with AI can accomplish what several developers previously accomplished?

What if QA becomes partially automated?

What if deployment becomes increasingly autonomous?

What if architecture can be generated and evaluated by AI?

What if project coordination itself becomes increasingly automated?

Then the question is no longer just about replacing a particular job.

It becomes a question about how many people are needed to produce the same amount of software.

And that is a much more uncomfortable question.

Because the answer could be:

Fewer people.

But there is an important problem with stopping the discussion there.

Even if AI can perform all these tasks, that doesn't automatically mean it should make every decision.

A technically possible solution is not necessarily the right solution.

The cheapest architecture may not be the safest.

The fastest implementation may not be the most maintainable.

The most scalable solution may be unnecessary for the actual business.

And a solution that looks perfect technically may still fail because it misunderstands what the customer actually wanted.

So perhaps the most interesting question isn't whether AI can do the work.

It is what happens when AI becomes capable of doing most of it, while humans are still responsible for deciding what should actually be done.

That leads directly to the next question.

But what if AI can do that too?
